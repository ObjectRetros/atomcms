# Contributing to Atom CMS

Keep each pull request focused on one feature, bug fix or refactor. Start from the latest `dev` branch and open the pull request against `dev`:

```bash
git switch dev
git pull --ff-only origin dev
git switch -c bugfix/descriptive-change
```

Use `feature/<descriptive-kebab-case>`, `bugfix/<descriptive-kebab-case>` or `refactor/<descriptive-kebab-case>` according to intent. Use descriptive Conventional Commit messages and a conventional PR title of at most 70 characters.

The PR body contains `## Why` with one or two short sentences explaining the reason and resulting behavior. Add `## Testing` only when reviewers need a manual checklist of commands, routes, actions and expected results. Automated verification belongs in CI and the task report.

## Implementation

Follow the repository's agent instructions and Laravel Boost guidance for the installed versions, backed by [Laravel 13 documentation](https://laravel.com/docs/13.x). Extend existing controllers, Form Requests, policies, services and emulator contracts where they own the behavior. Preserve supported themes, languages, clients and emulator capabilities.

The application uses `bootstrap/app.php`, `app/Http/Kernel.php`, `app/Console/Kernel.php` and providers registered in `config/app.php`. Follow those existing registration points when reading examples from the newer Laravel application skeleton. Use `config()` in application code; read environment variables in configuration files so deployment caching works.

## Laravel Boost

Use `APP_ENV=local` in your development `.env`. After installing dependencies or updating framework packages, run `composer boost:update` to regenerate the repository guidance, and review the resulting diff. Run `php artisan boost:install` to configure your preferred agent, MCP connection and skills locally. See [Laravel Boost](https://laravel.com/docs/13.x/boost) for the supported integrations.

## Checks

Install dependencies with `composer install` and `npm ci`. Run focused tests for the behavior changed, then the relevant existing checks:

```bash
composer lint
composer analyse
composer test
npm run build:atom
npm run build:dusk
```

The Pest suites require **two disposable MariaDB databases**, `testing` and `testing_ada` by default. They use `RefreshDatabase`, which drops and recreates tables. Configure credentials with access limited to those test databases, inspect `phpunit.xml`, and clear cached configuration before testing. Never point the suite at a hotel database. Arcturus and Ada test schemas are loaded automatically; see [test schema documentation](../../database/schema/README.md).

Run both emulator suites for shared model, database, permission or payment changes, and check the affected browser/CLI flow. A successful build alone does not prove runtime behavior.

Update the relevant pages under `docs/wiki/` in the same PR as behavior changes. These tracked pages can be reviewed alongside code; publishing the separate GitHub wiki happens only after the source changes have been reviewed and merged.
